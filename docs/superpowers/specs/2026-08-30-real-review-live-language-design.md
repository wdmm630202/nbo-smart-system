# 南铂真实体验卡：匿名联网与活语言引擎设计

日期：2026-08-30
状态：设计已在对话中分段确认，尚未开始实现或部署

## 1. 背景

当前 NFC 真实体验卡不是模型生成，而是从固定的开头、过程、结果数组中取句子，再放进 3 个固定结构。扩大短语数量、按日期轮换和保存近期历史只能减少完全相同的结果，无法消除统一的 AI 口吻，也无法跟随近期顾客表达变化。

本次改造把生成依据从“固定文案库”改为两部分：

1. 顾客当次提供的真实细节，决定文案能写哪些事实。
2. 30 天内有效的公开语言信号，影响表达节奏，但不得成为顾客事实。

系统继续坚持真实评价边界：不诱导五星、不虚构体验、不自动发布、不采集顾客身份。

## 2. 已确认的产品决策

- 允许匿名联网生成，但不发送姓名、电话、订单号、照片或其他身份信息。
- 顾客愿意用约 20–30 秒回答 3 个真实问题，不再追求“点两下直接生成”。
- 采用“匿名在线 AI + 每周低频语言雷达 + 语义查重 + 匿名反馈”的混合架构。
- 同行资料只用于提取语言规律；不得复制同行评价，不得把店家宣传当成顾客口吻。
- 原始回答默认只用于当次请求，不写入服务器数据库。
- 语言信号 30 天自动过期。采集失败不得静默使用旧资料。
- 第一阶段每日预计费用上限为 10 元人民币；达到应用侧上限后暂停生成并通知负责人。
- 先在独立测试地址试运行，达到验收门槛后才替换现有 `/nfc/` 页面。

## 3. 目标与非目标

### 3.1 目标

- 每篇评价只包含顾客明确提供或明确确认的事实。
- 同一批 3 篇结果在叙述角度、事实顺序、开头和结尾上明显不同。
- 近期顾客语言能在有证据、有日期、可过期的前提下影响表达。
- 顾客在手机上 20–30 秒完成输入，并能直接修改、复制和打开抖音。
- 负责人能看到生成健康、趋势新鲜度、重复度、费用和失败原因。
- 接口密钥、后台访问令牌和平台登录信息不进入前端源码。

### 3.2 非目标

- 不自动发布评价，不点赞、不评论、不操作顾客账号。
- 不生成顾客未经历的正面卖点，也不要求五星。
- 不建立顾客画像，不接入订单号、手机号、照片或 CRM 身份。
- 不在顾客点击生成时临时抓取小红书或抖音。
- 不把同行原文建设成永久文案库。
- 不在第一版同时建设多个生产模型提供商；前端只依赖稳定的内部生成协议。

## 4. 总体架构

系统分为 6 个相互隔离的单元：

1. **顾客端真实体验卡**：保留现有 GitHub Pages/NFC 入口，完成三步输入、本机脱敏、结果编辑和复制。
2. **Review Gateway**：独立 Cloudflare Worker，负责来源限制、服务端脱敏、模型调用、事实校验、重复检测、限流和费用保护。
3. **生成与验证器**：使用 OpenAI Responses API；生产模型名由 Worker Secret/环境配置指定，初始默认 `gpt-5.4-mini`。验证不通过时最多重写两次。
4. **活语言雷达**：在南铂本机使用用户控制的登录态，每周低频、只读研究公开内容，只上传提炼后的候选信号。
5. **D1 数据库**：保存语言信号、非可逆文本指纹、生成事件汇总、版本和经顾客主动同意的匿名改写样本。
6. **负责人后台**：用独立 Bearer Secret 访问，负责查看健康状态、审核信号、拉黑套话、暂停生成和运行验收样本。

数据流：

```text
顾客三步回答
  -> 浏览器本机脱敏
  -> Review Gateway 再次脱敏与验证
  -> 加载未过期语言信号和南铂真实性规则
  -> 模型生成 3 个结构化版本
  -> 事实支持检查 + 套话检查 + 批内差异检查 + 历史语义查重
  -> 通过后返回顾客页面
  -> 顾客修改、复制或重试
  -> 仅上传匿名事件；改写原文必须另行主动同意
```

`Review Gateway` 与现有客片网关独立部署、独立数据库、独立 Secret。可以复用现有网关的 CORS、D1 清理和测试模式，但不能共享顾客统计表或后台令牌，以缩小故障和权限影响范围。

## 5. 顾客端交互

### 5.1 页面原则

- 无需登录，一次只显示一个主要问题和一个主要下一步动作。
- 顶部显示 `1/3`、`2/3`、`3/3`，顾客可以返回修改。
- 点击立即有按压反馈；页面不使用妨碍输入的长动画。
- 尊重 `prefers-reduced-motion`、`prefers-reduced-transparency` 和文字放大。
- 不单独录制或上传语音。需要语音时使用手机系统键盘的听写能力，最终仍提交文字。

### 5.2 三个问题

#### 问题一：来之前，你最担心什么？

可选提示包括：不会摆动作、怕修得不像本人、担心额外消费、怕流程麻烦、其他、没有特别担心。顾客可以补充一句自己的话。

#### 问题二：现场哪个细节让你印象最深？

页面提示顾客描述一个真实动作或事件，例如摄影师具体怎样教、妆造哪里合适、选片时发生了什么。仅选择“服务很好”不算有效具体细节。

#### 问题三：现在最想写哪一点？

先选择满意、有好有坏、不太满意，再补充成片、价格、过程或交付感受。必须支持“暂未拿到成片”，避免模型虚构交付结果。

### 5.3 生成前条件

- 至少取得 2 个相互独立的真实事实。
- 如果只有泛化选择而没有具体细节，系统只追问 1 个自适应问题，不生成万能文案。
- 套餐选择是可选信息，不自动进入文案。顾客必须单独确认“想在评价里提到套餐”。
- 套餐名称、价格和包含内容从可更新配置读取，并带版本与更新时间；不得继续硬编码在顾客页面中。

### 5.4 三种输出

- **短一点**：约 50–90 字，允许自然省略和不完全对称的句子，不强求总结句。
- **讲过程**：约 100–160 字，按来店前、拍摄中、结束后的顺序表达。
- **说重点**：约 70–120 字，只围绕一个主要顾虑和一个具体结果。

三种名称只表示表达方向，不对应固定句式模板。页面可展开“这段根据什么写的”，展示该版本引用的事实标签。顾客可以修改后复制、打开抖音或系统分享，但系统不代替顾客发布。

## 6. 请求与响应协议

### 6.1 生成请求

前端只发送结构化字段：

```json
{
  "session_id": "random-ephemeral-id",
  "satisfaction": "positive | mixed | negative",
  "facts": [
    {
      "id": "fact-1",
      "category": "concern | onsite | result | package",
      "text": "顾客确认后的匿名事实",
      "source": "choice | free_text"
    }
  ],
  "mention_package": false,
  "package_snapshot": null,
  "client_prompt_version": "review-v3"
}
```

限制：请求正文最大 4 KB；单条事实最大 120 个中文字符；最多 6 条事实；URL、联系方式、订单号和疑似提示注入内容在进入模型前被隔离或拒绝。

### 6.2 生成响应

模型必须返回 JSON，网关只向前端放行验证后的字段：

```json
{
  "variants": [
    {
      "style": "short | process | focus",
      "text": "生成文案",
      "used_fact_ids": ["fact-1", "fact-2"],
      "used_trend_ids": ["trend-20260830-01"]
    }
  ],
  "meta": {
    "prompt_version": "review-v3",
    "trend_snapshot_at": "2026-08-30T00:00:00Z",
    "trend_mode": "fresh | customer_facts_only"
  }
}
```

必须恰好返回 3 种风格。`used_fact_ids` 必须来自本次请求；`used_trend_ids` 只能引用未过期、已批准的语言信号。

## 7. 生成、真实性校验与排重

### 7.1 提示层级

系统规则高于顾客文字。顾客输入作为引用数据传入，不作为可执行指令。模型必须遵循：

- 只写事实数组中的内容。
- 未提供“无推销、按时交付、像本人、价格透明”等事实时不得自行补充。
- 允许负面和混合体验，不把结果强行改成推荐。
- 不使用固定结束语，不要求给店铺打分。
- 语言信号只控制节奏、长度和具体程度，不能增加事件或结果。

### 7.2 四层验证

1. **事实引用检查**：每个版本必须返回事实 ID；不存在的 ID 直接拒绝。
2. **事实支持检查**：独立验证调用逐句判断是否能由所引用事实推出；任何不支持的句子都使该版本失败。
3. **表达检查**：阻止无事实支撑的万能夸赞、固定客服句、相同开头结尾和三版同序复述。
4. **语义排重**：为验证后的文本生成小尺寸向量和结构签名，与 90 天内的匿名指纹比较。超过经测试集校准的相似阈值时重写，而不是只检查完全相同字符串。

第一次验证失败后带着具体原因重写；最多重写 2 次。仍失败时不返回固定文案，而是返回 `needs_more_detail` 或明确的暂时失败状态。

### 7.3 禁止的默认套话

除非顾客事实本身明确表达对应意思，否则禁止直接生成：

- 整体体验很好
- 服务很专业
- 值得推荐
- 性价比很高
- 流程很顺畅
- 下次还会再来
- 给有同样需求的人参考

负责人后台可以维护禁用表达，但该清单只负责阻止坏表达，不作为反向模板库。

## 8. 活语言雷达

### 8.1 采集边界

- 每周运行一次低频只读研究；顾客请求不触发平台采集。
- 第一版以小红书公开笔记和评论为主。
- 小红书使用南铂本机、用户明确控制的现有登录态；不把 Cookie 上传到 Cloudflare。
- 抖音只有在存在稳定、合规的只读来源后才接入；不得绕过登录或平台限制。
- 不采集联系方式、私信、私域群或非公开客户资料。

### 8.2 来源分类

每条候选来源必须标记：

- `customer_experience`：可用于提取顾客语言规律。
- `store_marketing`：只用于了解卖点，不得影响顾客评价口吻。
- `suspected_sponsored`：默认不启用。
- `unknown`：默认不启用。

分类依据包括账号身份、是否出现完整卖点清单、是否有具体个人经历、是否同时包含保留意见、评论互动和来源上下文。分类结论是推断时必须保留低置信度，不冒充事实。

### 8.3 信号结构与启用规则

语言信号只保存：

- 近期顾虑类别。
- 叙述节奏和细节类型。
- 常见句长、语气强弱和是否带数字/犹豫/保留意见。
- 来源链接、观察日期、来源类型、可信度和到期时间。
- 不超过必要长度的转述摘要，不保存整篇同行文案。

信号至少满足以下一种条件才可启用：

1. 在 2 个独立顾客来源中重复出现。
2. 经负责人在后台人工批准。

信号自最后证据日期起 30 天到期。过期后停止参与生成；后台显示原因、最后成功更新时间和剩余有效信号。采集失败时进入 `customer_facts_only` 模式，不回退到过期资料。

## 9. 数据、隐私与留存

### 9.1 默认不保存

- 顾客三个原始回答。
- 顾客姓名、电话、订单号、照片、账号标识。
- 完整生成文案和顾客修改后的文案。
- 原始 IP 地址和平台 Cookie。

### 9.2 允许保存

- 90 天：不可直接还原的文本向量/指纹、结构签名、生成成功或失败、耗时、模型/提示版本、选择了哪种风格。
- 90 天：语言信号的来源链接、转述摘要、分类、可信度、批准状态和到期记录。
- 30 天：只有顾客主动勾选“匿名帮助南铂改进表达”时，保存该次生成前后匿名文本；到期后删除原文，只保留聚合统计和非可逆指纹。
- 长期：不含顾客文本的按日聚合指标、禁用表达和版本记录。

任何应用日志都不得记录请求正文、响应正文或 Secret。清理任务至少每日执行一次，并有自动化测试证明到期数据会删除。

## 10. 安全、限流与费用保护

- 生成接口只允许正式 GitHub Pages 域名、未来的南铂自定义域名和 `localhost/127.0.0.1` 测试来源。
- 管理接口使用独立 Bearer Secret；顾客端永远拿不到管理令牌。
- OpenAI API Key、模型名、管理令牌和费用配置只保存在 Cloudflare Secret/环境配置中。
- 使用 Cloudflare 边缘限流，不把原始 IP 写入 D1。默认单设备 10 分钟 5 次、每日 20 次；负责人测试令牌走独立受控额度。
- 请求大小、字段数量、字符长度和响应 token 上限都必须限制。
- 每日预计费用达到 10 元人民币时应用侧立即停止新的模型调用并通知负责人。费用按实际 token 和服务器配置的单价估算；该限制是应用保护，不替代模型提供商账户层的预算告警。
- 提供负责人一键暂停生成的 kill switch。

## 11. 负责人后台

后台只显示完成运营判断所需的数据：

- AI 接口健康、过去 24 小时生成次数、P50/P95 延迟和预计费用。
- 语言雷达最后成功时间、有效/过期信号数、顾客内容占比和失败原因。
- 三种风格的展示、选择、复制和重试比例。
- 事实验证失败率、需要补充细节比例、重复检测拦截率。
- 当前模型、提示、套餐配置和语言信号版本。
- 暂停/恢复生成、批准/拒绝候选信号、禁用套话、运行测试集。

后台不展示顾客身份，不提供单顾客追踪，也不允许通过指纹反查顾客。

## 12. 异常处理

| 情况 | 顾客端行为 | 后台行为 |
| --- | --- | --- |
| 顾客断网 | 回答保留在本机，可重新提交 | 不产生事件 |
| 模型超时或 5xx | 明确提示暂时失败，保留回答，不输出旧模板 | 记录无正文错误码、耗时和模型版本 |
| 语言雷达超过 30 天未更新 | 仅用顾客事实生成 | 红色显示 `customer_facts_only` 与失败原因 |
| 事实验证失败 | 最多重写两次；仍失败则追问一个细节 | 记录失败阶段和规则版本 |
| 触发限流 | 告知稍后再试，保留回答 | 记录聚合限流计数 |
| 达到每日费用上限 | 暂停在线生成，顾客仍能复制自己填写的原话 | 明确显示费用保护已触发 |
| 后台主动暂停 | 显示维护状态，不调用模型 | 保留恢复入口和操作时间 |

运行时绝不自动回退到当前固定语言库。旧版本只用于发布级回滚。

## 13. 测试与验收

当前仓库没有好评助手的独立测试套件。新实现必须增加隔离测试，不依赖现有无关的旧 starter 测试。

### 13.1 自动化测试

- 浏览器与服务器双重脱敏：手机号、订单号、URL、姓名提示样本。
- 请求 schema、大小、来源、限流和管理鉴权。
- 顾客未提供的事实不得出现在输出。
- 满意、混合、不满意、暂未收片四类场景。
- 三种版本的开头、结尾、事实顺序和长度差异。
- 禁用套话、语义近似和近期指纹拦截。
- 过期、未批准、低可信度语言信号不得进入生成。
- 30/90 天清理、日志不含正文、费用上限和 kill switch。
- 离线保存、重试、慢网、手机尺寸、文字放大、减少动画和减少透明度。

### 13.2 模型评测集

- 至少 50 组匿名测试经历，覆盖满意、一般、不满意和信息不足。
- 每组运行三种风格，并对同一输入重复生成，检查模板复现。
- 人工逐句核对事实支持；在该评测集中的事实编造必须为 0。
- 每批三种文案的差异检查通过率至少 95%。
- 未经事实支持的万能夸赞出现率必须为 0。
- 正常网络下 95% 的生成请求在 10 秒内完成。

### 13.3 真实顾客试运行

- 先邀请 10–20 名真实顾客使用测试入口。
- 完成时间中位数不超过 30 秒。
- 至少 70% 选择“像我本人说的”。
- 至少 60% 在最多重试一批后复制其中一个版本。
- 任何顾客或负责人发现虚构事实，立即停止替换正式入口并修正验证规则。

这些数字是上线门槛，不是对长期转化效果的保证。

## 14. 发布、回滚与系统总台

1. 在 `apps/reviews/nfc-beta/` 和对应 GitHub Pages 测试路径发布，不修改现有 `/nfc/`。
2. 完成自动化测试和 50 组评测集。
3. 进行 10–20 名真实顾客试运行。
4. 达到门槛后，将验证过的版本替换正式 `/projects/reviews/nfc/`。
5. 更新南铂智能系统总台中现有好评助手卡片的说明和状态，不创建重复项目卡。
6. 替换后保留上一个已验证提交作为发布级回滚点。

回滚是部署动作，不是运行时文案降级。在线生成失败时仍不得自动调用旧固定文案库。

## 15. 预计代码边界

实现计划应把改动限制在以下范围：

- `apps/reviews/nfc-beta/`：新顾客流程与本机脱敏。
- `workers/review-gateway/`：独立生成、验证、趋势、后台和 D1 网关。
- `tools/` 下独立的只读趋势整理/上传工具。
- `tests/` 下好评助手、网关、隐私和发布验证测试。
- `tools/export-github-pages.mjs`：导出测试页及最终正式页。
- `docs/projects/reviews/`：仅由导出流程生成的静态产物。
- 南铂智能系统总台现有项目卡：正式替换时更新状态与说明。

不得顺手重构无关的客片、封面、ERP 或其他网关代码。
